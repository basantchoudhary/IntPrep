The sandbox is standing and maintained, not built during an incident — reproduction is minutes, not hours.  ·  The regression agent that proves the fix is the same one that gated the release, so a fix cannot pass a lower bar than the original deployment did.
The problem

Assurance stops at go-live, monitoring is built separately from the readiness checks, and Ops carries well-understood toil at 3am.

What we need

Monitors that are the gate's checks, a standing sandbox to reproduce in, and an escalation ladder that makes automation safe in a regulated estate.

The line we hold

The agent proposes and proves a fix in the sandbox. Production is changed through the project's own pipeline, gated by action class — never around it.

Self-healing is not the goal. Fewer incidents is the goal. A rising auto-heal count on the same check means we are masking a defect, and the system is built to say so.

Architecture & Design

Bounded authority · mandatory validation · complete evidence

Action classes — what the agent is permitted to do

Class 0
ObserveNo change is made
Agent
Notify, annotate, raise a ticket. Used during change freeze and whenever a human already owns the incident.
Class 1
Reversible, no state changeRestores service without touching data or config
Agent
Retry an idempotent run · restart a worker · scale out · fail over to a replica. Executes automatically, then validates.
Class 2
Reversible, touches data or configOnly within pre-declared bounds
Agent in bounds
Reprocess a partition · quarantine bad records · revert config · resize a cluster. Dry-run in a sandbox first; auto-revert if validation fails.
Class 3
Irreversible or regulatedSchema, deletion, credentials, anything GxP-relevant
Human only
The agent diagnoses, prepares the change, drafts the rollback plan and assembles the evidence. A person executes it. No exceptions, no override flag.

Deterministic — most of the loop

Detection, the action-class decision, the runbook action itself, validation, revert, and the evidence record. Replayable and explainable years later.

Agentic — one step

Diagnosis. Correlating telemetry, logs, recent changes and topology into a hypothesis — and explaining it in language an on-call engineer can act on.

Human — the boundary

All class 3 actions. Every escalation. Accepting anything the learning loop proposes into the spec. The spec is only ever changed by a person.

Composed from the same base agents
  • Sandbox Creator (code · config · data) — the standing replica the fault is reproduced and the fix proven in
  • Reverse Engineer IaC (CI/CD for code, platform, config) — rebuilds the sandbox, ships the fix through the project's own pipeline, and rolls it back
  • Regression Agent (functional & non-functional) — Test Harness Creator plus Data Expectation Service. The same agent Ops Gate runs, so a hotfix is held to the bar the release was accepted on

Three agents, two capabilities. Nothing here was built for self-healing — it was already built for the gate.

Guardrails that stop the healer
  • Rate limit — max 3 actions per workload per 24h, then escalate
  • Repeat guard — the same fix twice raises a defect instead of a third fix
  • Freeze windows — observe only during change freeze or validation periods
  • Human incident open — never act underneath someone who owns the problem
  • Blast radius — beyond N downstream consumers, propose rather than act
  • Kill switch — per workload, per domain, global
Every heal produces the same kind of evidence record as the gate itself. An automated change without an audit record is an audit finding. The record is the deliverable, not the fix.
Backup 1

Worked incident — a data quality breach, end to end

Class 2 action · sandbox dry-run · validated · recorded
02:14:06
Detect — monitor FUN-03 breached

Day-2 monitor, deployed from the check that passed the gate. pass_rate 96.1% < 99.5%. Same rule, same evaluator, same threshold as the gate used.

02:14:09
Diagnose — agent forms a hypothesis

Profiles the current batch against baseline, correlates with the upstream watermark and the last deployment. Finds status contains a value outside the accepted set, confined to one source partition, starting with a vendor release 40 minutes earlier. Confidence stated, evidence linked.

02:14:11
Decide — policy resolves the action class

Runbook for FUN-03 maps to quarantine_bad_records, class 2. Guardrails checked: no change freeze, no open human incident, 0 prior actions in window, 1.9% of rows affected — inside the 1% bound? No. Exceeds bounds → downgraded to propose only.

02:14:12
Remediate — bounded, so it stops

The agent does not act. It prepares the quarantine change, dry-runs it in a sandbox to show the resulting pass rate would be 99.8%, drafts the rollback, and pages the on-call engineer with all of it assembled.

02:31:40
Human approves; agent executes and validates

Engineer approves the prepared change. Agent applies it, then re-runs FUN-03: pass_rate 99.8%. Passes. Had it failed, the change would have been reverted automatically and the incident escalated.

02:31:44
Record & learn

Evidence record written: trigger, diagnosis, class, bound breach, dry-run result, approver, action, validation. Learning loop proposes a new check — "accepted_values on status enforced at ingestion, not curation" — targeted at specs/base.yaml. A human decides whether it becomes part of the bar.

The interesting moment is 02:14:11 — the agent had a correct diagnosis and a working fix, and still stopped. That is the design working. Bounds are not a limitation to apologise for; they are the reason this is deployable in a regulated estate.
Backup 2

Failure modes of the healer itself

"What happens when the thing that fixes things is wrong?"
Failure modeWhat it would causeControl
Wrong diagnosis A correct-looking fix applied to the wrong cause The agent never chooses the action — the runbook does, from the check that fired. Diagnosis informs the human-readable explanation, not the decision.
Flapping Fix and break in a loop, burning the estate Rate limit (3 per workload per 24h) and repeat guard (same action twice → stop and raise a defect).
Masking a real defect The system looks healthy while a bug persists for months Repeat-heal rate is reported as a defect signal, not an efficiency win. Two heals of the same fault open a defect automatically.
Remediation makes it worse An outage caused by the recovery, not the fault Class 2 dry-runs in a sandbox first; validation re-runs the failing check; failure triggers auto-revert and escalation.
Acting during a human incident Two actors changing production simultaneously Open human incident forces observe-only. The agent annotates and stands down.
Scope creep beyond the workload A local fix with estate-wide consequences Blast-radius check against the recovered topology; beyond N downstream consumers it proposes rather than acts.
The healer itself is down Silent loss of monitoring — the worst case Monitors fail closed and page a human. Absence of signal is treated as failure, exactly as at the gate.
Policy drift Bounds quietly widened until the ladder means nothing Policy is versioned code, reviewed like the spec. Every evidence record stamps the policy version it acted under.
Every one of these is answered by a control that exists in the policy file, not by a promise.
Backup 3

Measures and rollout

Earning the right to act, one class at a time

Measures

MTTDTime to detect — should approach the monitor interval
MTTRTime to restore, split by action class
Auto-revert rateRemediations that failed validation — the honesty metric
Repeat-heal rateSame fault healed again — should fall, not rise
Rollout — authority is earned
  • 1 · Observe — class 0 only. The loop runs end to end and recommends; nothing acts. Compare its recommendation against what the engineer actually did.
  • 2 · Shadow — the agent prepares class 1 actions and a human clicks. Measures whether the recommendation was right before it is trusted.
  • 3 · Class 1 automatic — restarts, retries, scale-out. Reversible, no state change.
  • 4 · Class 2 in bounds — with sandbox dry-run and auto-revert, one workload at a time.
  • 5 · Never class 3. That is not a later phase. It is the design.
Why this is the reusable pattern
  • No second checklist — monitors are generated from the gate that already exists
  • The action-class ladder is domain-agnostic; only the runbooks are domain-specific
  • Policy ships as versioned code, reviewable by security and enterprise architecture
  • The evidence record satisfies the audit question before it is asked
  • Ops Gate, Self-Monitoring and Self-Healing are one artefact used three ways, not three products
The strongest thing we can say about this system is what it refuses to do. Class 3 is permanently out of reach of automation — and that is what makes classes 1 and 2 acceptable.
