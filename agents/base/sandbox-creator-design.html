Base Agent

Sandbox Creator — Design

agents/sandbox_creator/ · demonstrated, not asserted
The problem it removes

Every handover pack says rollback is tested and the infrastructure is reproducible from code. Both are sentences. Nobody re-runs them at the gate, because running them means touching an environment — so the two controls that matter most on a bad night are the two nobody verifies. Ops finds out whether rollback works at the moment it needs rollback to work.

The promise

Take a disposable copy of the project, actually execute the rollback and the deploy inside it, and report the exit code and the duration. The claim becomes a measurement. When the script is missing the check does not pass quietly — it fails closed, because an unexecutable rollback is worse than a documented one.

Deterministic — all of it

Copy, execute, time, capture, destroy. There is no model in this agent at all. An exit code is not an opinion, and the whole value of the agent is that the same project produces the same evidence every run.

Agentic — only downstream

The agent produces the observation; explaining why a rollback failed from 600 characters of stderr is a comprehension task, and it happens in Ops Gate's remediation layer, not here.

Human — the acceptance

A rollback that succeeds in 0.4 s on a copied directory is evidence, not proof of production recoverability. Whether the sandbox is representative enough is a judgement Ops makes once, when the project declares its scripts.

The difference between a claim in a handover document and evidence is that one of them has an exit code. This is the agent that makes "we tested rollback" a falsifiable statement.

  "succeeded":  true,

  "output":     "reverted to previous version"
}

# script absent — note what this is NOT
{
  "executed":  false,
  "succeeded": false,
  "detail":    "script not found: ops/rollback.sh"
}
# -> Evidence.unavailable -> status ERROR, never PASS
The design rule this agent exists to enforce

Nothing passes by absence. A project with no rollback.sh is not a project with a trivially clean rollback. The collector converts a missing script into Evidence.unavailable(...), and the engine maps that to ERROR — which fails the gate exactly as a broken rollback would.

This is the single most common way an assurance tool lies: the check that cannot run reports green. It is worth saying out loud, because it is a design decision, not an accident — the code path for "cannot verify" was written before the code path for "verified".

Failure modes of the agent itself
  • Script hangs → 60-second timeout, exit code 124, timed_out: true. A hung rollback is a failed rollback.
  • Script is destructive to real infrastructure → the sandbox isolates the filesystem, not the network. A script that calls a live cloud API is not contained. Mitigation is a convention — ops/*.sh target the environment named in the project config, and the gate runs against non-production.
  • Copy is not the environment → the agent proves the script runs and exits clean; it does not prove the production estate would recover. Stated as a limit, not hidden.
  • Output truncation → capped at 600 characters, deliberately: evidence bundles are audit records, not log stores.
Reuse beyond Ops Gate
  • Ops Self-Healing — a proposed fix is applied in a sandbox and validated before it touches the real system. That gate is this agent; without it, self-healing is just automated damage.
  • Spark / Databricks Modernization — the modernized job runs beside the original in an isolated copy, so equivalence is demonstrated rather than argued.
  • Any category B judgement needing observed behaviour — the SLO-realism assembler is the first, and the pattern generalises: when the question is "is this claim true in practice", run it.
One primitive — run it somewhere disposable and watch what happens — used by three capabilities. Nothing above this agent reimplements execution isolation.
