Base Agent

Data Expectation Services — Design

agents/data_expectations/ · declaring nothing is not passing
The problem it removes

"Data quality is covered" is the most common sentence in a handover pack and the hardest to falsify. Rules live in a tool nobody opens at the gate; reconciliation was run once, by hand, during UAT. Worst of all, a project that declared no expectations scores the same as one whose expectations all pass — because a rate over zero rules is vacuously perfect.

The promise

Profile the data, evaluate the declared expectations, reconcile source against target — all as arithmetic, no model anywhere. The gate rule is defined > 0 and pass_rate >= 99.5, so silence fails. And when a project declared nothing, the agent derives the expectations it should have had and hands them back.

Deterministic — all of it

Profiling and rule evaluation are arithmetic. There is no reason to involve a model, and involving one would cost the property that matters most: the same dataset and the same rules give the same pass rate in three years, in front of an auditor.

Agentic — naming the semantics

The agent can derive that a column is never null. It cannot know the column is a patient identifier. Attaching business meaning to a derived rule is the one place a model earns its seat — as a suggestion on a proposal, never as an applied rule.

Human — committing the rule

A proposal describes one sample of data. Turning it into an expectation is a statement about all future data, and that is a data owner's call. The agent writes the file; a person commits it.

A pass rate over zero declared rules is not a pass — it is an empty measurement wearing a percentage. defined > 0 is four characters of rule that close the most common assurance gap in data.

The rule vocabulary, derivation, and its limits

What Ops Gate gets · what a proposal is not

Expectation vocabulary

ExpectationBreach reported as
not_null"3 null(s)"
unique"2 duplicate(s)"
between {min, max}"7 value(s) outside range"
accepted_values [..]"unexpected: ['PENDING']"
anything unrecognised"unknown expectation 'x'" — counted as a failure
Why an unknown rule fails rather than skips

A typo in an expectation name is the quietest way to disable a control. Skipping it would leave the pass rate at 100% while the rule does nothing. Failing it makes the typo visible in the same release it was introduced — the check that cannot be evaluated is never the check that passes.

A proposal is an observation, not a rule
  • between derived from one sample will be too tight. Today's maximum order value is not tomorrow's ceiling. Committed as-is, it turns a good day into an incident.
  • unique may be an accident of the sample — small extracts are often incidentally distinct.
  • Which is exactly why the output is a file in .opsgate/remediation/ with a header telling the reader to review it, and why nothing is applied automatically.
  • The value is not the rule. It is that the blank page is gone and the conversation starts at review rather than authorship.

Failure modes of the agent itself
  • No dataset declared → Evidence.unavailable → ERROR. A project that names no data does not get a data-quality pass.
  • Whole-file read. CSV is loaded into memory — right for gate-scale samples, wrong for a production table. The interface is the contract; the implementation behind it is replaceable with a warehouse-side query without any consumer changing.
  • A column of mixed types profiles as string, so no range is proposed. Silent, and acceptable — under-proposing is safer than proposing a wrong range.
  • Sampled data passes where full data would fail. The gate evidences what it was pointed at; which dataset it is pointed at is a declaration in project.yaml, and therefore reviewable.
Reuse beyond Ops Gate
  • Ops Self-Monitoring — the expectations that passed at the gate become the day-2 monitors verbatim. One artefact, authored once, doing gate duty and production duty.
  • Ops Self-Healing — a DQ breach is the highest-signal diagnosis input there is: it names the column and the observed value, which is most of a root cause already.
  • Spark / Databricks Modernization — reconcile() is how a modernized job is shown to produce the same numbers as the one it replaces.
The same rules run at the gate and in production, because they are the same file. That is what makes assurance continuous rather than a date in a project plan.
