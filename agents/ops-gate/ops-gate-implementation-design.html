Design

Ops Gate — Implementation Design

170 items · unstandardised evidence · no mandate
The trap

Treating each item as automated or manual. That forces 170 adapters before the gate is worth anything, so it never ships — and the items that resist automation get quietly dropped, which means the tooling silently becomes the bar.

The move

Every item enters at Level 0 and climbs independently. The gate ships complete over all 170 on day one; adapters only move items up. Promotion never rewrites a rule, because rules are written against a normalised vocabulary, not against a tool.

The verification ladder

0Declared
The project asserts it, with a name and a date Gate stores the assertion itself declared · missing
1Evidenced
The project points at an artefact Gate fetches and hashes it into the bundle evidenced · missing · error
2Verified
Nothing new — the adapter fetches it Observed values + a deterministic rule verdict pass · fail · error
3Continuous
Nothing new — the same rule, on a schedule Time series after handover pass · fail · error

Ships complete on day one

All 170 live at Level 0. That version already beats a document review: every item carries a name, a date, and a waiver register with no blanks.

Promotion is additive

Moving an item from 0 to 2 adds an adapter and a rule. No other check changes, no consumer changes, no bundle format changes.

The maturity number is real

Share of applicable items at Level 2+. Starts at ~15% and rises — a far better story than one claiming 80% on day one.

"Isn't Level 0 just self-certification with extra steps?"

Two things stop it. One: declared is a distinct status from pass — it appears differently in the report and never counts toward the maturity number. Two: a profile sets a minimum level per severity. Tier 1 sets requires_level: {blocker: 2}, so a blocker that is only declared does not pass at tier 1. Tier 3 leaves it at 0. This is where the tiering earns its keep.

You never standardise the input. You standardise what the adapter emits. That single decision is what lets 170 items and an unknown number of platforms coexist.
Decisions

Seven decisions, with their reasoning

Recorded as decisions so the reasoning survives the next argument
#DecisionRationaleReversible
D1Every item enters at Level 0 and climbs independently. No item is dropped for being hard to verify.Otherwise the bar silently becomes "what our tooling can see".No — spine
D2Normalise what the adapter emits, never the input. Rules target a fixed field vocabulary per domain.One rule covers Azure DevOps, GitHub Actions and Jenkins. Skipping this gives 170 bespoke rules and collapse within a year.No
D3Three fixed tier profiles. No per-project profiles; relief comes only through waivers, which are visible and expire.A negotiable bar is not a bar. Three profiles means three conversations, ever.Yes
D4Item text is global; severity is per profile. OWN-04 is Blocker at tier 1, Major at tier 2, absent at tier 3.Fixes the 89-blocker problem without touching the checklist. An overlay is just a map of id → severity.Yes
D5The PoC wires three platforms: repo scan, CI results, cloud resource + tag state.These need only a repository and one cloud account — plausibly obtainable without a programme.Yes
D6Ask for attachment, not veto. The bundle is attached to the acceptance record; it does not block the pipeline.Veto is political and gets negotiated. Attachment is administrative and does nearly the same work.Yes
D7declared is a distinct status from pass. Level 0 satisfies an item without claiming verification.The bundle must never imply a machine checked something a human asserted.No
Assumption still to confirm

D5 assumes an Azure-centric estate with Databricks and Azure Monitor. If GSK's actual stack differs, adapter sizing changes and nothing else in this design does — which is itself the point of D2.

Three of the seven are non-negotiable: the ladder, the field vocabulary, and declared ≠ pass.

The manifest does more work than the automation does

A project that cannot say where its alerting configuration lives has failed MON-01 before any tool ran.

Filling it in is the readiness conversation — held months earlier than it would otherwise happen, and in an hour rather than a workshop.

Two rules that keep it filled in
  • Keep it small. If it reads as a form, nobody completes it.
  • Convention over configuration. Adapters probe the conventional locations first, so the manifest is mostly overrides.

declarations.yaml — the Level 0 assertions

declarations:
  RES-06:
    stated: true
    by:   raj.patel@gsk.com
    date: 2026-05-14
    note: "Restore tested into rg-orders-dr on 14 May,
           completed in 42 minutes."

A declaration without by and date is incomplete and reads as missing. The note is what a reviewer actually reads.

profiles/tier-2.yaml — thin overlay

profile: tier-2
extends: base

verdict:
  requires_level: { blocker: 1 }   # t1=2, t3=none

severity:                    # only the overrides
  OWN-04: major
  RES-07: minor

exclude: [REG-02, REG-07, SEC-11]

attestations.yaml and waivers.yaml already exist and are unchanged — signature, role, date, expiry; and a blank is not a waiver.

The project declares where, never what. Everything else the gate fetches for itself.
Process

Seven stages — and the one where tools usually lie

Ordering matters
1ResolveTier → profile → the applicable subset, with per-item severity and levelUnknown tier is an error, not a default
2CollectBy level: L0 reads declarations · L1 fetches and hashes the artefact · L2/L3 call the adapterUnavailable is a first-class result. Never a pass
3EvaluateDeterministic rules, L2+ only. Parsed to an AST, walked against a whitelist — a spec cannot execute anythingA rule that cannot be evaluated is error
4AssembleCategory B only: gather, cross-reference, and state the specific question a human must answerStatus is needs_review regardless of what comes back
5VerdictPure rules over statuses, plus the profile's requires_level floorNo model involvement, ever
6RemediateWhere a base agent can produce the missing artefact, produce it into .opsgate/remediation/Proposals only. Nothing is applied
7SealHash the bundle, stamp spec version and profile, take the signatureA failing gate cannot be signed as accepted
Status vocabulary

Two statuses are new — the rest already exist in the implementation.

  • pass · fail — Level 2+, a rule decided
  • declared (new) · evidenced (new) — satisfied, but not verified
  • needs_review — category B, awaiting a human
  • attested · missing — a named signature, or its absence
  • waived — reason, approver, expiry, all present
  • error — evidence unreachable
Stage 2 is where assurance tools quietly lie

The check that cannot run reporting green is the single most common way one of these systems becomes untrue. Zero findings across zero files is no scan, not a clean scan.

error and missing always fail closed. declared and evidenced satisfy an item but are excluded from the maturity number and are subject to requires_level.

Nothing passes by absence — written as the first code path, not added later as a fix.

The property this buys

Adding Jenkins alongside Azure DevOps means writing one adapter that emits the test and release vocabularies.

Zero checks change. That is the reuse argument in one sentence, and it is measurable rather than asserted.

The request that destroys it

"We just need one custom field for this project."

Grant it twice and rules become bespoke; grant it ten times and the system is 170 special cases nobody can change. Custom values go in the note, never in a rule. D2 is the one to defend hardest, because each individual violation looks harmless.

An adapter's only job is to speak the vocabulary, whatever the source speaks.
Classification

"Cannot be automated" is five different problems

Conflating them is why teams either over-automate or give up
Reason it resistsExample itemsTreatmentCan AI help?
Needs judgementPRF-02 · RES-11 · DQ-05Category B: the agent assembles, frames the question, and a human decidesYes — highest value

Row three contains every item that will be contested

RES-06, ACC-02, ACC-03, PRF-03 — all contested for the same reason: they require doing the thing rather than describing it.

The honest answer is not to infer them. It is to make performing them cheap and self-evidencing. Turn the act into its own evidence rather than trying to detect it afterwards — the sandbox rollback already works this way, and the trick generalises.

Assembly tasks worth building, in value order

1Runbook coverage — do runbooks cover every failure mode in the RES register? MON-03, DOC-03
2Architecture currency — does the document match the recovered topology? DOC-01
3Undocumented failure points — already built; the template for the rest RES-02
4SLO realism — declared target vs sandbox-observed behaviour PRF-02
5Manifest drafting — read the repo, propose the manifest, so the team edits rather than authors

Number 5 is not obvious and matters most. It reduces adoption friction more than any individual check — and adoption, not coverage, is the actual constraint.

If an item's status depends on a model's opinion, it is category B and stays there. No exceptions for convenience — the exception is what gets asked about in an audit.
Packaging

What should be a skill, and what should not

Over-decomposition buys version skew and nothing else
ThingSkill?Why
The gate itselfYes — existsOperator-facing, portable, adoptable by a team without adopting our tooling opinions
A "prepare for the gate" self-checkYes — build thisProject-side. They run it because it helps them. Adoption without politics
Evidence adaptersNoConnectors behind a contract. One skill per adapter is over-decomposition and buys version skew
The assembly tasksThree or fourPrompt-heavy and judgement-adjacent, so genuinely skill-shaped — but not thirty of them
The self-check is an adoption strategy, not a feature

An Ops-side gate is compliance, and gets resisted.

The same spec handed to a project team as "run this and see what you'd fail — and I'll draft your manifest" is help, and gets adopted.

Same file. Opposite politics. It is also, directly, the shift-left stage of the rollout plan.

Why one repository, not five
  • The base agents and the gate share one contract — the check spec. Splitting them buys version skew and contradicts the composability thesis.
  • Each agent is a package depending only on contracts/, so any one could be lifted out without unpicking imports.
  • Repo strategy is not the same thing as module boundaries — worth saying explicitly if asked.
Ship the bar as something adoptable. A pattern that needs its author present is a consultancy engagement, not a reusable asset.

⚠ Migration hazard — the two ID schemes collide

Implemented CFG-01 is drift. Checklist CFG-01 is secrets. Same identifier, different meaning.

The migration must be a rename with an explicit mapping table, not an overlay. A silent mis-map here would be very hard to spot and would invalidate every bundle produced before it was found. Re-run one known bundle before and after and diff it.

Adoption

Earning a mandate a PoC cannot be granted

The goal is not to hold the mandate — it is to make granting it cheap
#MovePermission neededWhat it produces
1Retrospective run on 2–3 already-accepted projectsNone artefacts exist, nobody is blocked"Passed the manual review, would have failed 6 blockers — and 2 of 3 early incidents map onto them"
2Shadow the next real handoverInformal"It found things the review missed"
3Publish the self-checkNone opt-inAdoption nobody had to mandate
4Ask for attachmentOne sponsorFormalises what already happens
Steps 1 and 3 need nobody's permission

That is the point. On step 1, fill the manifest yourself so the project team carries zero cost — which also removes the only reason they would say no.

Political caution on step 1

Running this against a colleague's live system is warm. Frame every output as what the bar would have caught, never what that team got wrong. Anonymise where you can, and run the first one on a project you were close to, so you can be blunt about your own.

Ask for attachment, not veto

"The bundle is attached to the acceptance record" is administrative and gets waved through. "The gate blocks production" is political and gets negotiated into nothing.

Attachment does nearly the same work: a failing or unsigned bundle on the record is visible to everyone who reads that record afterwards. The blocking behaviour then emerges without anyone having to grant it.

Mandate follows evidence — it does not precede it.

Open items

  • Define the three tier profiles concretely: exclusions and severity overrides
  • Severity down-grading pass — 89 blockers is a tier-1 reading; D4 makes the fix cheap but the grading still has to be done
