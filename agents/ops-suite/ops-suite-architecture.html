Nothing above the spine owns a rule. Rules live once, in versioned code, and are consumed by the gate, the monitors, the healer and the resolver alike.
One spec, four consumers

The checks that gate a release become the day-2 monitors, the validation after a heal, and the bar a hotfix must clear. There is no second checklist to drift.

One evidence shape

Gate verdicts, heal records and L2 resolutions all emit the same bundle: what was checked, what was observed, who signed. One audit story, not three.

Composed, not duplicated

Three base agents serve four capabilities. The Regression Agent that proves a hotfix is the same one that gated the release — so a fix cannot pass a lower bar.

Four capabilities, but one artefact and one set of agents underneath. That is the difference between a suite and four products that happen to share a name.

The lifecycle — one closed loop

Build → gate → run → detect → heal → escalate → learn → back to the spec

7bNot validated, or no runbook→ L2 ResolverAuto-revert, then escalate with everything already gatheredInvestigation context
8InvestigationL2 ResolverReproduce in sandbox → diagnose → propose and prove a fix. No reproduction, no fix proposalEvidence pack + proven fix
9FixHuman + CIEngineer applies it through the project's own pipeline; the Regression Agent verifiesResolution record
10LearnLearning proposerDrafts a new check, threshold or runbook so the next occurrence is automatic — or prevented at the gateProposed spec change
11RatifyHumanA person accepts it into the versioned spec. The spec is only ever changed deliberatelyNew spec version
Where the loop closes

Step 10 feeds step 1. Every unknown fault L2 resolves becomes a known one — handled automatically next time, or prevented at the gate. Production teaches the checklist; a human ratifies it.

Where it escalates

Two doors into L2: no runbook exists, or the runbook ran and validation failed. Both arrive with context already assembled, which is the point.

Where humans are mandatory

Steps 3, 9 and 11 — acceptance, applying a fix, and changing the bar. None of the three is ever automated, at any maturity level.

Eleven stages, three of them human, and every one of them producing a durable record. The audit trail is not a feature bolted on — it is what the system emits as it works.
Architecture 4

Interfaces between components

The artefacts that cross boundaries — the real contract surface 
// CheckSpec — Git, versioned, the single source of truth
{ spec_version, domain, owner,
  checks: [ { id, title, category: A|B|C|D, severity,
              evidence: { source, mode? }, rule?,
              on_fail: { agent }, day2: { schedule, alert },
              attestation?, waiver? } ],
  verdict: { fail, conditional, pass, signature } }

// Evidence — what a collector returns. Absence is failure.
{ values: {...}, available: bool, detail }

// EvidenceBundle — emitted by Gate, Heal AND Resolve
{ bundle_version, generated_at, target,
  spec: { version, domain, owner },
  summary: { total, by_status, automation_pct },
  verdict: { outcome, reasons },
  results: [ { id, category, status, observed, message,
               remediation } ],
  signature: null | { name, role, decision, signed_at } }
// Day2Manifest — gate output becomes monitoring input
{ generated_from, spec_version,
  monitors:      [ { id, source, rule, schedule, alert } ],
  not_deployed:  [ id ]        // failed the gate
}

// HealRecord — the same bundle shape, plus
{ trigger: { monitor_id, observed },
  diagnosis: { hypothesis, confidence, evidence[] },
  action: { class, name, bounds_ok, dry_run },
  validation: { check_id, passed, reverted },
  policy_version }

// InvestigationContext — Heal → L2 handover
{ incident, failed_check, attempted_action,
  telemetry_window, topology, recent_changes,
  prior_incidents[] }

// Base-agent returns — stable, small, testable
DriftReport      { resources_differing, missing, unmanaged, changed[] }
SandboxResult    { executed, succeeded, duration_s, output }
RegressionResult { suites_failed, coverage_pct, dq_pass_rate,
                   variance_pct }
Why one bundle shape

Gate, heal and resolve emit the same structure. Auditors learn one artefact; tooling parses one schema; and a question like "show me everything that changed this workload this quarter" is one query rather than three integrations.

Why base agents return data, not objects

Small JSON-serialisable returns keep the agents independently testable, recordable for replay, and swappable without touching the consumers.

Why the spec is the only shared mutable

Every other artefact is append-only. One thing changes deliberately and under review; everything else accumulates. That is what makes the system reconstructable.

Six artefacts is the entire integration surface of the suite. Components are replaceable precisely because the things that cross between them are this small.

Why collectors run in the execution plane

They sit beside the workload, inside its network and its permission boundary. The control plane receives observations — counts, rates, booleans — never rows. That keeps a central service out of the data path and out of scope for most data-residency questions.

Why sandboxes are ephemeral

Created per task, destroyed on completion including on failure. Nothing accumulates, nothing needs cleaning up, and a leaked sandbox cannot become a shadow copy of production data.

What we deliberately do not build

No new observability backend, no new ticketing system, no new catalog. The suite integrates with what exists; the only stores it owns are the spec and the evidence.

The suite is small because it stores almost nothing. Two owned artefacts — the spec and the evidence bundle — and adapters onto everything else.
Architecture 6

Identity, security and cross-cutting concerns

What each component may do, and what it may never do

Authority model

Read
Collectors & base agentsEvidence gathering
Workload identity
Read-only against the workload's own systems. No collector holds a write credential — the capability simply does not exist in the code.
Execute
Sandbox CreatorIsolated execution
Sandbox identity
Full rights inside a disposable copy, none outside it. Rollback and dry-runs are proven here before anything touches production.
Act
Remediation executorClass 1 and bounded class 2
Scoped service identity
Only the actions bound to a runbook, only within declared bounds, only outside freeze windows, always followed by validation.
Sign
Acceptance, class 3, spec changeIrreversible or regulated
Named human
Production acceptance, GxP-relevant change, and any change to the bar itself. No override flag exists.
Security properties, enforced in code
  • Fails closed. Unreachable evidence is an error, never a pass. Zero findings across zero files is no scan, not a clean scan
  • Rules are data. Parsed to an AST against a whitelist — a spec file cannot execute anything
  • No silent skips. Every check is verified, attested or waived with an approver and an expiry
  • Signature integrity. A failing gate cannot be signed as accepted; overriding a blocker is a separate, visible waiver
  • Least privilege by absence. Components lack the credentials for what they must never do
Cross-cutting
  • Observability — one span schema across all four capabilities: spec version, policy version, check id, outcome, duration, cost
  • Audit — every bundle stamps the spec and policy version it was judged against
  • Cost — the suite's own spend is attributed per workload, like any other consumer
  • Idempotency — every remediation carries a key; a retry cannot act twice
  • Kill switch — per workload, per domain, global
  • Determinism — same spec and same evidence produce the same verdict, today and in three years

Failure modes of the suite itself

Evidence source down

Check fails closed and is reported as error, distinct from fail — an outage never reads as a defect

The suite is down

Monitors fail closed and page a human. Absence of signal is treated as failure

Spec rot

Versioned and owned; every bundle records the version it was judged against, so drift is visible

Gaming the thresholds

Coverage and DQ sampled independently by Ops after handover

The strongest security property here is what the components cannot do. Not policy, not configuration — capabilities that were never granted, in code that was never written.

Why this order

Strictly dependency-driven. Phases 0–3 are the foundation everything else composes from, which is why phases 4–11 are additive rather than foundational — each reuses components that already run.

Value arrives at phase 2

Ops Gate is useful alone, with no monitoring and no healing. Nothing here requires the whole suite to exist before anything works.

What is deliberately last

Class 2 remediation and the learning loop. Authority is earned after the observation phases have shown the recommendations were right.

Fifteen of twenty-six components exist and run today. The remaining eleven compose from them — which is the test of whether the base-agent decomposition was real or just a diagram.
