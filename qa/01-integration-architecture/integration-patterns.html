The three-plane topology

Software · agentic · human — and the bar everything must cross

Read it top to bottom. Humans set intent and receive typed approvals. Agents plan, delegate and propose. Nothing reaches the software plane without crossing the deterministic bar — and the bar is not part of the agent, so it cannot be reasoned around.

The bar is the architecture

Every arrow from the agent plane to the software plane passes through one deterministic component. That is the whole safety argument in a single visual.

A→H is an arrow, not a chat

Typed approval object with evidence, blast radius, reversibility and expiry. If it can't be replayed a year later, it isn't a control.

The bottom row didn't change

System-to-system integration is still events, contracts and CDC. The agentic layer sits on top of the estate — it doesn't replace how the estate talks to itself.

03

Inside the bar — the validating adapter

The A→S edge, zoomed · where the design budget goes

Five deterministic checks, three exits. The agent's proposal is never executed directly — it is validated, classed, budgeted, then executed under a credential the agent never holds. Reject rather than coerce is the critical detail: coercing a malformed call into a valid one is how you get a confidently wrong action.

The rule this diagram encodes

The agent never gets raw access — no direct SQL, no admin API, no shell. Shared-database integration was already an anti-pattern between two deterministic services; it doesn't become acceptable because the caller is now an LLM.

Why this is the reusable asset

This adapter is a template, not a per-project build. Every MCP server in the estate inherits authz, validation, budget and audit by construction. That is what makes "reuse" a fact rather than an aspiration — and it's the T3 evidence.

04

The deterministic / agentic pipeline

Observe → propose → validate → execute → record, with its branches

Four of five stages are deterministic. The LLM occupies one — the stage where judgement is genuinely required — and has no authority in any other. Rejection loops back to a bounded re-plan; irreversible and privileged actions divert to a human before execution; evidence is emitted by the run rather than assembled before an audit.

Say this

Most people demo an agent that decides. This one is explicitly designed so the agent proposes and the deterministic control plane disposes — which is precisely why it can go into a GxP-relevant path at all. The non-determinism is boxed in on both sides.

05

Same shapes, new names

Four classic EIP patterns — and their agentic labels
Split by content

EIP · content-based router  →  Agentic · classify-then-dispatch. The classifier changed from a rule to a model. The shape, the failure mode and the need for a default route did not.

Fan out, then combine

EIP · scatter-gather  →  Agentic · parallel subagents. New wrinkle: workers can now disagree, so the aggregator needs a conflict rule — majority, highest-confidence, or escalate.

Coordinate a multi-step job

EIP · process manager  →  Agentic · orchestrator–worker. The plan used to be static. Now it's generated — so it needs a depth cap, a budget and a termination condition the coordinator cannot talk itself out of.

Handle what fails

EIP · dead letter channel  →  Agentic · parked run. The failure mode to avoid is an agent silently retrying forever. Failed runs are parked, visible and triaged — never swallowed.

Say this

Four diagrams, eight names. The shapes are twenty years old — that's not a criticism, it's the reason I can put agents into a regulated estate with a straight face. We're not starting from zero on safety; we're applying a mature catalogue to a new kind of caller.

06

Blast radius — scope tools, not intentions

The bulkhead pattern, applied to agents
The formula

Blast radius = the union of what every tool in that agent's scope can reach. Not what it's likely to do — what it can do.

Prompts and instructions are guidance. The credential and the tool list are the control. "We told the agent not to" has never been an acceptable answer to a security architect.

The follow-up, and the answer

"What if an agent genuinely needs broad access?"

It doesn't get one agent with broad access. It gets several narrowly-scoped agents and a deterministic orchestrator holding the composition — which is the right-hand diagram. The orchestrator has the breadth; no single agent does, and the orchestrator isn't an LLM.

07

The trust boundary

Control plane vs data plane — this generation's SQL injection

The single rule: content flows up as data and is never promoted to instruction. A document can tell the agent a fact; it can never tell the agent what it is allowed to do — because authority comes from the control plane, which the data plane cannot reach.

The honest concession — make it early

It's this generation's SQL injection: untrusted data crossing into the control path. But with SQLi we got parameterised queries — a complete structural fix. There is no equivalent complete fix here yet, and I'd be wary of anyone who says there is.

Which is why the defence is architectural

My primary control isn't detection, it's capability scoping — assume the agent can be hijacked and make sure a hijacked agent still can't do much. I can't stop injection. I can bound the consequence, and that's the design goal.

08

Agent-to-agent delegation

Treat it as untrusted inter-service messaging — because that's what it is
When splitting is right

Different scope, data sensitivity, credentials, owner or release cadence — the same reasons we split services. That's bulkheading, and it's the reuse story: composites are assembled from base agents rather than built from scratch.

When it's theatre

Multi-agent as a performance strategy — five agents chatting to reach an answer one could have reached. Cost, latency and an unbounded failure surface, bought for a diagram.

The failure mode

A wrong output from agent one becomes an established fact for agents two, three and four. So: provenance and confidence in the message, validation at every hop — not just the first.

Say this

This is the same class of problem as trusting an internal service just because it's inside the perimeter. We learned that lesson once already — I'd rather not learn it twice.
